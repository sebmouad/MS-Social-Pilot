# Analytics reads and comparisons

Implemented batch, 2026-10-16. This document describes stored-data reads, not complete analytics or live provider coverage. The architecture contract remains the required target.

`modules/analytics/server/read.ts` owns UI/HTTP/CSV/MCP snapshots. Each call rechecks the active user, current membership, entitlements, feature permission, workspace purge state and channel grants. Caller channel constraints intersect current grants. Export checks the reports feature separately. Explicit empty resource selections remain empty. Unknown/unavailable selected IDs fail closed; date/channel/metric filters never widen authority. Available account reads follow the current connection-source permission model, not a separate ad-account grant system.

The input vocabulary is `start`, `end`, `compare`, `filter`, `channel`, `adFilter`, `adAccount`, `search`, `metric`, `page`, `pointPage`, `rowPage`. `filter=1` and `adFilter=1` distinguish explicit selections from all available resources. Repeated scalar inputs, invalid calendar dates, reversed/oversized ranges, unavailable IDs, duplicate resource IDs and invalid page numbers are rejected. Repeated channel/account inputs are preserved. Provider metric keys are opaque bounded strings and must match the current catalog. Duplicate catalog keys fail closed.

Dates are inclusive UTC calendar days. Default range length is capped by the configured maximum. Previous-period comparison uses an immediately preceding equal number of days; prior-year comparison clamps February 29 to February 28, so leap-year calendar windows can have different lengths. Both windows are shown in the interface. Comparisons require matching metric semantics, full coverage and the exact covered resource ID set. Missing, partial, changed-coverage and category/unsupported totals do not produce growth. A nonzero value over a zero baseline has an absolute delta and no invented percentage. Percent ratios use percentage-point changes in the UI. This is observational comparison, not attribution or statistical significance.

`platforms/facebook/analytics.ts` alone interprets provider metrics and legacy storage. Known additive daily counts sum across dates; unknown numeric metrics and unique/reach counts use conservative latest-per-resource totals while retaining dated observations. Mixed scalar/category shapes become separate catalog entries. Audience is the newest valid stored measure per selected channel at or before the report end. Summed audience/reach is not deduplicated people. Provider aggregation caveats flow to UI, CSV and both MCP tools. CPP/frequency use the latest stored day and coverage from accounts contributing reach on that day; per-account details retain their own as-of dates.

Ad accounts remain independently selectable with no channel selected. An all-resource member can read selected enabled accounts on an ads-only connection. Limited channel members only see accounts from their currently granted channel connection sources. User filters do not grant access to a new source.

## Interfaces and configuration

- `/analytics`: permission-aware scoped shell; metric cards and detail tables. Navigation, dates, comparison, resource selection, metric search/detail selection, export and pagination belong to the contextual sidebar/phone drawer.
- `GET /api/analytics`: same read service and validated input, safe typed failures and no-store on all responses.
- `GET /api/reports/export`: same full matching snapshot, independent of visible metric/detail pagination. CSV includes totals, dated values, resource/category rows, coverage, aggregation notes and comparison provenance. Formula-like text is escaped. The configured row ceiling is disclosed; truncation has a CSV marker and HTTP headers.
- MCP `get_analytics_overview`, `get_analytics_metric_details`, and `msp://analytics/overview`: same snapshot authority. Metrics, audience and selected channels have bounded continuation; detail points/rows can be read to the end. Comparison, ad-account selection and metric search are supported. The old `get_page_analytics` tool was removed: its separate raw read could replace an exact target ID with a scope filter and bypass requested-resource ownership. It is neither advertised nor dispatched.
- Root → Product modules → Analytics consumes registry version 39: default/max window, metric/detail page sizes, preview chart points, search length, resource-selection ceiling and CSV row ceiling. Existing keys retain their persisted names; `analytics.reportMaxChannels` now bounds both channel and account selections on every Analytics read.

## Boundaries still open

The read engine loads normalized window data before presentation pagination. It has not been load-tested at production volume and is not a database-streaming analytics engine. Very large available-resource catalogs need an independently paginated selector; exceeding the default selection ceiling currently requires an explicit smaller selection. Error pages preserve raw filter URLs with sidebar retry/reset; comprehensive inline correction and field errors remain part of broader form UX work. CSV is bounded and not an unlimited archive export; MCP has result bounds in addition to product limits.

Facebook currently reads stored channel insights and account-level ad insights. Additional API fetch coverage, post/campaign/ad-set/ad analysis, complete historical category snapshots, pinned metrics, richer audience segmentation, ranked posts, report schedules/templates, other formats and live provider correctness remain unfinished. Unknown metrics use conservative semantics until provider metadata is established. Existing Instagram scaffolding is unavailable and is not a complete engine. Labels/copy and all cross-module configuration coverage are not complete merely because these Analytics operational keys are active.

No migration, remote test content, background worker or production cutover is part of this batch. Legacy production stays running.
