# Replacement background worker

Run the rebuild worker beside the web process with `npm run worker` from `app/rebuild`. Root controls it with `jobs.enabled`, the five-field cron expressions for posts, analytics, inbox, purges, and unused image cleanup, `storage.orphanMediaRetentionDays`, `storage.orphanMediaBatchLimit`, `sync.maxConcurrentJobs`, `sync.maxItemsPerJob`, `sync.workerLeaseMinutes`, `sync.workerHeartbeatSeconds`, and `sync.retryLimit`. Cron is evaluated in the worker host's local timezone. The worker reloads these values every five seconds. Image cleanup is tenant-scoped, examines at most the Root-configured `storage.orphanMediaBatchLimit` UUID image files per workspace per run, and only removes files older than the configured retention period when no post in that workspace references the image. Post status does not affect retention. The manual `DELETE /api/media/:id` endpoint uses the same reference check and refuses in-use images.

The posts job publishes due local queue items through the same lifecycle used by the UI, after rechecking the author's current workspace, feature, and channel permissions. It also reads remote Facebook status and reconciles destinations already marked `scheduled_remote`. A destination claim prevents duplicate submission after an ambiguous provider response; such records require manual reconciliation. Analytics stores daily Page snapshots and account-level Ads Insights for enabled connections. Inbox sync stores Facebook conversations, returned messages, and comments for enabled Page connections. Each read is scoped by the local workspace, enabled selection, active Facebook connection, unexpired credential and required inbox or ads read scopes. Database upserts make repeated runs safe.

Each job has a database lease so multiple worker processes cannot run the same scheduled job at once. Leases renew while work runs and are released by token, so an expired worker cannot release a successor's lease. Every attempt appends a row to `rebuild_sync_runs`; the shared worker heartbeat and latest-job summary tables support operational health. Root can inspect recent outcomes through the rebuild Root runtime configuration page once its job-health panel is enabled.

Transient provider reads retry up to Root's configured retry limit with exponential delays capped at one minute. Work is bounded per connection by `meta.pageSize * meta.maxPages` and runs serially within a job, while the number of concurrent jobs follows Root's limit. A crashed worker's lease expires after the Root-configured duration. The additive migration `20261023100000_rebuild_worker_jobs` must be applied before starting the worker. Never run migrations against production without the deployment review and backup process described in the rebuild README.

The job scheduler and cron matcher have local unit tests. These tests do not make live Graph API calls; verify provider permissions and stored writes against a non-production database before cutover.

## Jobs/productivity lane jobs (2026-10-22)

All four run through the same runner with leases and `rebuild_sync_runs` history above:

- `retention` (`retention.schedule`, nightly): prunes workspace activity/email/click-detail/AI/report-run history plus installation error and worker-run history. Feeds, insight snapshots, link totals, running reports, identity/members/content are never touched. Each run writes one Root receipt with counts. Owners/admins can also prune their own workspace now from Settings › Data (exact confirmation, audited).
- `sharingDeadlines` (`sharing.deadlineSchedule`, every 5 minutes): approves pending-review posts inside each live deciding link’s `publishAnywayHours` window through the Publishing review lifecycle as the link creator. Revoked, expired or rotated links, departed creators and moved posts are skipped, never forced.
- `scheduledAgents` (`agents.scheduledRunsSchedule`, hourly): claims due scheduled agents (workspace-timezone weekday + `lastRunOn`) and writes their drafts as the creator with hourly AI metering; nothing is scheduled or published. AI failure frees the day so the next run retries.
- `bestTimes` (`publishing.bestTimeApplySchedule`, weekly): adds the strongest evidence-backed new times to channel queues for workspaces in automatic best-time mode, claiming the week per workspace and auditing each addition.
