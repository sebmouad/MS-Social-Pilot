# Client sharing and public bio (W2)

Status: host-integrated batch79b candidate with isolated automated and actual local HTTP/MCP/PostgreSQL/Chromium evidence. Expanded verifier and final compiled CSS desktop/phone checks passed within the coverage described below. No live-proxy or production proof. Sharing (`settings/sharing`) and the bio page (`settings/bio`) are separate features, pages, API areas, MCP tools and Root groups.

## Scope
- Share kinds: `review`, `calendar`, `portal` (review + calendar tabs). Portal "results" (analytics) is not offered.
- Owner control (owner/admin only, own plan feature `settings/sharing`, current channel scope): create, list, edit, deliberately renew, revoke, rotate, delete and view client answers. Consequential writes require exact API/MCP confirmation; customer UI generates it after a consequence checkbox. Metadata-only edits require no secret-rotation confirmation. Each write uses one transaction, actor re-check and audit.
- Bio control (own feature `settings/bio`): read, save (create/replace with ordering and per-link click totals), delete.
- Public routes: `/share/[token]`, `/share/[token]/media/[id]`, `/api/sharing/public/[token]/decision`, `/bio/[slug]`, `/bio/[slug]/go/[id]`.
- Owner UI: `/settings/sharing` (table, create/confirm/secret/answers dialogs, paging) and `/settings/bio`. Owner API: `/api/sharing/links`, `/api/sharing/links/[id]`, `/api/sharing/links/[id]/feedback`, `/api/sharing/bio`.
- MCP (`modules/sharing/mcp.ts`, access map in `semantics.ts`): `list_share_links`, `list_shareable_channels`, `list_share_feedback`, `create_share_link`, `update_share_link`, `revoke_share_link`, `rotate_share_link`, `delete_share_link` (feature `settings/sharing`); `get_bio_page`, `save_bio_page`, `delete_bio_page` (feature `settings/bio`). Same services as UI/API.

## Authority (rebuilt per call, in `server/access.ts`)
Active account and membership as owner/admin; `settings` module and the area's own feature in the plan; that feature's read/write permission, **narrowed by an MCP key ceiling** (`actor.permissionCeiling`, deny-only) and channel ceiling (`actor.allowedTargetIds`, an empty list means no channels); workspace not suspended for writes; no erasure running (reads and writes). Result ceilings: `executeSharingTool(..., ceiling)` and `SharingReadOptions.maxItems` cap page sizes (links, answers, channels, bio links); the bio owner view reports `truncated`, and the Settings UI refuses to save a truncated page so links are never silently dropped.
Inside every write transaction `lockActor` re-reads role, disabled account, suspension, **fresh purge state (new statement after the lock)** and module switches, so a change committed after the preflight wins.

## Transactions (no nested pool use)
`transact()` is one `prisma.$transaction`: shared workspace row lock (`FOR SHARE`, so erasure/suspension cannot pass), a per-workspace advisory lock (serialises "links per workspace"), then the work. It no longer wraps itself in `withWorkspaceOperation` (that helper holds its own pooled connection; nesting a second transaction inside could exhaust the pool). Public decisions never hold a sharing transaction while the Publishing lifecycle runs. A failed audit insert (row count ≠ 1) aborts the change.

## Security model
- Tokens: 32 random bytes, base64url. Only `sha256(token)` is stored (same digest as legacy). The secret path is returned once at create/rotating edit/rotate (HTTP also returns an absolute `url`) and never audited, logged or listed.
- Every unresolvable link (bad shape, unknown, revoked, expired, suspended workspace, erasure running, creator lost authority) yields the same not-found. Malformed tokens never reach the limiter or the database. Links without `expiresAt` are never served until explicitly renewed.
- The link only carries the creator's current authority: active owner/admin, `settings/sharing` entitlement and permission, current channel scope; `decides` is dropped when the creator lost approval permission.
- Public data: only selected enabled channels with current same-workspace non-invalidated connections and enabled/entitled platforms, post text, https link/media, planned/published time, public status label (`Waiting for your decision` / `Planned` / `Published`), channel name/picture. **Drafts, rejected and failed posts are never served**; review shows `pending_approval` only (approved/scheduled posts no longer leak into review), calendar (and the portal's calendar tab) shows `scheduled` and `published` explicitly. **Publishing ceiling:** a link serves nothing (same not-found) unless its creator can currently read the Publishing features its kind shows (`review`→`publishing/approvals`, `calendar`→`publishing/calendar`, `portal`→both; entitlement + permission, rechecked on every public request), and creation, rotation and access-changing edits require the same read for the actor **narrowed by the key ceiling**, so a Settings-only key cannot mint a link that serves posts. Owner feedback lists withhold post status/preview when the actor/key cannot read Publishing; client names/comments (Sharing data) stay visible. Never author ids, remote ids, errors, approval notes, token data or storage paths. Pages send `noindex` and `referrer: no-referrer`.
- Uploaded images are previewed through `/share/[token]/media/[id]`: the token must resolve (own `media` rate bucket) **and** a post the link currently shows must reference that exact image; everything else is one 404. Served `nosniff`, sandbox CSP, `no-store`. Non-image uploads are only counted.
- Rate limits (in-process, Root-bounded; `server/rate.ts`): page opens, image requests, decisions per address (plus per link, `sharing.decisionLinkFactor` × the per-address allowance), counted bio clicks. The store is **separate from `server/rate-limit`** (sign-in windows) and bounded by `sharing.rateStoreCapacity` (expired first, then oldest dropped), so arbitrary public keys can never evict login windows. Tokens/slugs are shape-validated before any bucket exists. Without a trusted proxy (`TRUST_PROXY`) the address is unknown; each **existing** link/page then has its own anonymous bucket scaled by `sharing.anonymousVisitorFactor` and is counted only after the link/page was found, so guessed keys create no window. Consequences, stated honestly: with an unknown address, lookups of non-existent tokens are not throttled by the app (indexed digest lookup; throttle at the proxy); counters are per process, reset on restart, and are not shared across processes or replicas; a large multi-address flood can still reset other public windows (bounded memory), never login ones.
- Bio public page and click redirect also require that some **active workspace owner** still holds the `settings/bio` entitlement and permission (successful grants are always rechecked; only refusals are cached per process for `bio.availabilityCacheMs`, with Root owner-scan and negative-cache-capacity bounds). Redirect targets are owner-saved http(s) URLs re-validated at read. Clicks are a capped integer; no address, agent or referrer is stored.
- Unique violations from raw queries (`P2010` + database `23505`) map to a conflict.

## Client answers and approval effects
`submitDecision` re-resolves the link, rate-limits, validates, then for approve/request-changes on a deciding link calls the Publishing review lifecycle as the link creator (`ReviewPort`, default adapter `reviewPost`) **with a `ReviewParticipant`**. `before` runs `lockPublicLinkForMutation` inside the lifecycle's own transaction: under `FOR SHARE` it requires that **the presented token digest is still the stored one** (a rotation after resolve loses), the link is unrevoked, unexpired and deciding, the workspace is not suspended or being erased, the creator is still an active owner/admin, and under `FOR NO KEY UPDATE` that the post is still `pending_approval` and lies wholly inside the link's enabled channels. `after` writes the `review_decisions` row plus a content-free `sharing.client_answer_recorded` audit (ids, decision, applied, comment length, never name or body) in the same transaction as the status change. Any failed check is the same not-found. The note Publishing stores and copies into its generic activity log is a fixed marker ("Approved/Changes requested by client via share link"); the client's name and full comment live only in `review_decisions`, so long comments always settle and no free text spreads into generic logs.
Failures are classified, not swallowed: `conflict` records nothing; `not_found` is not-found; **only** a `forbidden`/`unauthorized` refusal (the creator may no longer approve) keeps the answer as advice, in one separate Sharing transaction (same fresh checks, insert and audit with `reason: authority_refused`) and the visitor is told the team decides; every other error (database, participant, unknown) rolled the review back, stores nothing and is reported as `upstream_failure` ("could not be confirmed"), never as a received answer. Plain comments, answers on non-deciding links and advice use that same single transaction (`reason: comment | link_cannot_decide | authority_refused`); Sharing never nests a transaction around the Publishing review. A post also going to channels outside the link cannot be decided by the client. The owner sees each answer with the post's **current** status (the actual effect), never an assumed one.

## Legacy, bio and rotation behaviour
- Migrated links with no `expiresAt` are never served and show as expired. Rotating such an unrevoked link is the renewal path: it gets a new secret and `sharing.defaultExpiryDays` (audit `renewedForDays`). Revoked or date-expired links cannot use the simple rotate operation. Explicit versioned editing with expiresInDays can renew date-expired links; revoked links remain revoked.
- Saving the bio page keeps the **id and click total** of every link whose label and address are unchanged (printed `/bio/<slug>/go/<id>` addresses survive edits); new or changed links get new ids and start at 0.
- Raw-query unique violations (`P2010` with database `23505`) map to a conflict (`isUnique`); media of revoked/unresolvable links and uploads not referenced by a currently shown post answer the same 404.

## Editing and customer confirmation UX
The owner list returns an opaque version fingerprint covering editable fields and the secret hash. PATCH and update_share_link require expectedVersion; stale changes return conflict without overwriting. Metadata edits preserve the address. Access edits (kind, channels, window, comments, decision rights or lifetime renewal) atomically rotate it and return the new secret once. Rotating a deciding credential requires current approval write, even if decides was already true or is being switched off. Settings-only keys cannot mint any Publishing credential. Metadata rename, revoke and delete remain available without Publishing read because they mint no capability.

New links require explicit selected channel IDs; an empty or missing list never grants all channels. Valid legacy stored empty selections retain their historical meaning; malformed stored values fail closed publicly. Customer dialogs use meaningful checkboxes, preserve fields after failures and offer explicit reload on an optimistic conflict. Bio save/delete use consequence checkboxes and internally construct the same exact backend confirmation. The desktop link table fills its panel; editor fields retain a readable measure. Phone tables scroll locally.

## Host integration
Registry version71 installs module-owned configuration under Settings Root groups. Manifest, entitlement and permission maps expose separate Sharing/Bio features; owner/admin access only. Workspace MCP has eleven tools plus two resources and uses the same application services. Sharing writes own their workspace transaction and are excluded from outer MCP locking. One-time secret results must never be added to generic MCP request/result audits. Public routes remain outside sign-in gates; visitor identity requires a correctly configured trusted proxy. No proxy proof is claimed here.

The public decision endpoint counts actual streamed bytes against sharing.decisionBodyMaxBytes rather than trusting Content-Length. Bio successful authority checks are never positively cached. The generic runtimeConfigBatch validates a single non-secret setting snapshot and rejects unknown, secret, malformed or encrypted values.
