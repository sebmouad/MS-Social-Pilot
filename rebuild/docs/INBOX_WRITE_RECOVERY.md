# Inbox write recovery

Status: **partly implemented; remote deletion journal and MCP deletion are not shipped**. This plan implements the existing architecture contract; it does not reduce Inbox or full application scope.

## Implemented boundary

Local resolve/reopen belongs to `modules/inbox/server/workflow.ts`. Shared access rechecks active identity, membership, feature write permission, selected Inbox-capable channel scope and workspace state. Current caller constraints intersect member grants. Expired credentials can retain local workflow control because no provider write is made. A scoped database update and domain audit commit together. UI, HTTP and MCP dispatch through this service. The service refreshes authorization after a possible lock wait and owns one workspace operation guard; transports must not wrap it in another transaction on a different connection.

HTTP actions preserve only typed public errors, mask unexpected exception text and use no-store for all responses. Non-sync writes require an explicit successful service receipt. UI accepts only a valid success receipt; sync additionally validates every displayed count and timestamp. Missing/false/malformed receipts and lost responses preserve input/dialog state and describe an unconfirmed outcome. These boundaries do **not** establish provider idempotency or durable reconciliation.

## Required remote-deletion implementation

1. **Keep product orchestration neutral.** Inbox owns intent, concurrency, local persistence, history and UI/API/MCP behavior. The selected platform owns credentials, grants, request/response semantics and a normalized confirmed/rejected/unconfirmed outcome. No shared Graph codes or provider URL rules. Remove the current provider-owned local delete/audit orchestration only when its shared replacement is fully tested.
2. **Add a dedicated durable operation journal.** Use an additive migration under the application repository's migration directory, not mutable Root audit rows. Store an opaque operation ID, workspace, product/action, provider/channel, local object and durable remote identity or its protected equivalent, safe state/reason metadata, actor and timestamps. Unique resource identity includes workspace, provider, channel, object kind and remote identity; local comment ID alone is insufficient. No credentials or message content. Commit started intent before the one outbound attempt. Keep separate append-only domain audit events.
3. **Model uncertainty honestly.** Distinguish started, definitive rejection, remote-confirmed, locally completed and uncertain states. Only one claimant may contact the platform. A crash/timeout/lost response after dispatch cannot automatically release the resource for another remote attempt. Remote-confirmed operations may retry their idempotent local finalizer; local cascade, completion state and audit commit atomically. A lost confirmation-persistence response remains recoverable through the journal and provider/operator verification. Provider permission errors must never be interpreted as proof an object is absent.
4. **Serialize competing operations and prevent resurrection.** Coordinate delete with replies/moderation and concurrent sync writes for the same remote identity. Shared workspace locks protect purge/suspension ordering but do not serialize individual comments. Persist appropriate deletion tombstones and consult them when sync stores stale provider results, including replies under a deleted parent. Define explicit rejection/retry and tombstone-retention policies rather than deleting evidence on a timer. Rebind local cleanup safely if a remote item has multiple local aliases.
5. **Expose authorized recovery.** Require current membership/feature/channel permission and exact object-specific confirmation for every write interface. Return opaque operation/status/local-confirmation metadata only. Keep uncertain deletion in its dialog with a status/recovery action, without claiming deleted. Add scoped status/history tools and Root module-owned recovery controls before advertising MCP deletion. Root recovery must validate and audit its action; a switch cannot implement missing provider verification. Register all operational timeout, retry/recovery, history and retention policy in the typed registry with honest consumers.
6. **Integrate lifecycle and cutover.** Decide journal/tombstone ownership in export, retain/delete disconnection and workspace erasure; erasure must not strand active remote work or make deleted remote content eligible for an accidental retry. The current data-control code discovers workspace-FK tables, so new ownership cannot be left accidental. Update the checksum-pinned cutover migration inventory, schema verifier and documentation. Back up and restore-verify the isolated preview before applying new schema. Production remains gated by the full cutover contract.

## Evidence required before claiming completion

- Database tests prove committed intent precedes dispatch, unique claim under concurrency, no second provider call after uncertainty, idempotent local finalization and atomic audit/completion.
- Scope tests cover disabled/revoked users, narrowed keys, cross-workspace links, unselected resources and changed grants on re-entry.
- Race tests cover reply/moderation/sync versus deletion and purge/suspension lock ordering.
- HTTP/MCP/UI tests cover exact confirmations, every receipt state, transport loss, unconfirmed persistence, preserved context and operator recovery.
- Export/erasure/retention tests, reviewed additive migration and backup/restore rehearsal pass.
- Real authorized provider tests confirm outcomes on both sides and clean identifiable test content. Synthetic local or mocked provider tests cannot replace this gate.

Other Inbox gaps remain: assignment, private notes, saved replies, visitor-reply discovery and broader legacy parity. Follow LEGACY_CAPABILITY_PARITY.md and ARCHITECTURE_CONTRACT.md.
