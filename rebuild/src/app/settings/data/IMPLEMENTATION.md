# Workspace data controls

The Data and privacy settings page exports a JSON snapshot of workspace details, memberships, posts and destination links, connection metadata, inbox history, and stored Page and ad metrics. It omits provider access and refresh tokens and the instance-wide `root_activities` audit history. The export is generated on request, sent with `no-store`, and is not persisted by the app.

Deleting workspace data requires an owner or admin and the exact confirmation `DELETE`. Before confirmation, the page requests counts for mapped records and every additional table with a direct foreign key to `workspaces`. The operation persists a purge job and captures the canonical media root. A database transaction then locks the workspace row, enumerates direct workspace-owned tables from PostgreSQL's catalog, removes their rows, and relies on verified cascading foreign keys for dependent records. Workspace identity and memberships remain. The timeout is managed by Root. An audit event with aggregate row counts is written in the same transaction. A follow-up phase removes the workspace's media and export directories, then marks the job complete and audits file counts. If file removal fails, the owner or admin can retry the same request without rerunning database deletion. The database migration installs write gates on direct workspace-owned legacy tables while a purge is pending. A rollback-only rehearsal in an isolated legacy schema verified that these gates reject a new label during a purge and permit it after completion.

The JSON export remains limited by the rebuild's partial Prisma compatibility view and does not yet include all legacy feature records or media bytes. Storage cleanup covers the workspace trees beneath Root's configured `storage.mediaRoot`, including orphan files there; it refuses symlinks and special files rather than following them. External provider content and installation-wide audit details are not removed. Do not describe the current JSON export as a full backup. The worker resumes `requested` and `db_deleted` jobs on the Root-configured recovery schedule, retaining the original requester and API key identity in audit records. A failed cleanup remains pending for the next run. Publishing, Inbox, Ads, OAuth discovery, and MCP write entry points hold a shared workspace row lock through provider calls and local writes; purge requests acquire an exclusive lock on the same row before queueing. Root controls the operation and lock-wait timeouts. Scheduled publishing uses the same boundary. Provider-read-only background syncs still use a status check and database write trigger, so they can fail harmlessly rather than reinsert data during a purge.

Disconnecting a social source offers two local choices. Retaining history disables its channels and ad accounts while keeping records. Delete mode first previews counts for mapped channels, ad accounts, insights, inbox messages and comments, destination links, and posts that will become orphaned. It removes those mapped records; a post with links to other channels remains. The preview is an estimate and does not count cascaded rows in unmapped legacy tables. Delete mode is blocked while posts remain scheduled at the provider. Neither choice removes remote posts or revokes authorization at the provider. The choice and actual affected counts are audited.

Authenticated MCP exposes `preview_workspace_data_deletion`, `export_workspace_data`, and `delete_workspace_data`, plus a read-only deletion-preview resource. These reuse the UI data-control service, require the `settings/data` feature and owner/admin role, and apply the same purge rules. MCP deletion additionally requires `DELETE WORKSPACE DATA <workspaceId>` and records a bearer key ID in the transactional audit event when one is used.
