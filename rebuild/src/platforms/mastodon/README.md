# Mastodon module — staged, unavailable to customers

Provider-local fixture implementation covers per-instance app registration, OAuth URL/code exchange, authenticated account discovery, text/link publishing with an idempotency key, local image/video multipart upload and bounded processing checks, ownership-checked status and deletion. All operational policy is declared in `mastodon.policy`, loaded with runtimeConfig. Default access is disabled and every installed manifest capability remains unsupported. The adapter also declares every capability unsupported; this is not a complete customer integration.

The caller must supply an SSRF-safe transport. It must resolve and pin only public addresses, defend against DNS rebinding, refuse redirects, enforce the supplied timeout plus bounded response bodies, handle non-success HTTP status as errors, and redact credentials. The adapter deliberately has no fetch fallback. Syntax validation does not establish server trust.

OAuth callback URLs must be derived by the shared host from trusted requestOrigin, not incoming arbitrary host headers. The authorized service must persist the server origin alongside encrypted per-server app ID/secret and user access token, bind signed expiring single-use OAuth state to workspace/user/origin, and revalidate owner/member/viewer, entitlement and selected resource scope for every operation. None of those controls are claimed by this standalone adapter.

The manifest and settings are registered as staged through platforms/index.ts. Remaining integration edits: add provider-owned connection persistence/host assembly and register the host in shared server/platforms/index.ts; allow provider-owned instance metadata in credential hydration (the current PlatformCredential carries only a token and scopes); provide the pinned safe transport; wire authenticated shared services to existing UI/API/MCP with confirmations and audit; add role/cross-workspace tests and complete the MCP_PARITY integration mapping. Do not enable capabilities until these pass. No new product operation, UI screen, REST endpoint or MCP tool is exposed here.

Remote-only media URLs are rejected: the host must provide inspected local bytes. Mixed video/image sets, excess media, unknown formats and native scheduling are rejected rather than silently truncated. Unresolved uploads stop before status creation. Ambiguous writes are uncertain and are never automatically re-sent. Inbox replies/analytics from legacy are not implemented; their capabilities remain unsupported. Provider protocol strings (OAuth grant/response types, wire field names and multipart keys) are isolated here. Root API paths permit no embedded query or origin.

Evidence: `tests/mastodon-platform.test.ts` uses synthetic transport fixtures; no live Mastodon, browser, production, token storage or end-to-end shared-service verification has occurred. Legacy sweep must remain partial pending those integrations.
